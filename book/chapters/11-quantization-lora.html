Quantization, LoRA, and Fitting in Memory

Each chapter until now assumed that the model fits. This chapter is about what to do when it does not. Its two techniques are the reason that a laptop can run and adapt models that are much too large for it.

The number that decides everything

Before any technique, do the arithmetic. To train one parameter with Adam in float32, you need four tensors:

TensorBytes per parameter
weight4
gradient4
Adam first moment $m$4
Adam second moment $v$4
total16

That is sixteen bytes for each parameter, plus activations. A model with one billion parameters needs 16 GB before any activation exists. Take the memory of your machine, and subtract what the operating system already uses. Assume that you can really allocate approximately 70% of the rest. Full fine-tuning has a limit of approximately that value divided by sixteen bytes. On most laptops, that is less than a billion parameters.

Inference is very different: 4 bytes for each parameter in fp32, 2 in fp16, and 0.5 at 4-bit. The gap between those two cases is the full subject of this chapter.

Move the parameter count to 7B, and change between the modes. Full fine-tuning is impossible by two orders of magnitude. 4-bit inference is comfortable. Quantization plus LoRA takes you from one to the other.

Quantization

Represent a tensor of floats with a small set of integer levels at equal spacing. The simplest scheme is symmetric quantization:

$$s = \frac{\max|W|}{2^{b-1}-1} \qquad q = \operatorname{round}(W/s) \qquad \hat{W} = q\cdot s$$
Example — 8-bit, worked
w = [0.00, 0.15, −0.42, 0.98, −0.07, 0.31] max|w| = 0.98, and at 8 bits qmax = 2⁷ − 1 = 127 s = 0.98 / 127 = 0.007717 w w/s q q·s error 0.00 0.0 0 0.0000 0.0000 0.15 19.44 19 0.1466 0.0034 −0.42 −54.42 −54 −0.4167 0.0033 0.98 127.00 127 0.9800 0.0000 −0.07 −9.07 −9 −0.0694 0.0006 0.31 40.17 40 0.3087 0.0013 every error is below s/2 = 0.00386 ✓

Six floats (24 bytes) became six int8 values plus one float scale (10 bytes). The largest weight has no error, because it sets the scale.

Key concept The error is at most $s/2$, and the single largest magnitude in the tensor sets $s$. One outlier weight stretches the grid for each other weight that shares its scale. That one sentence is the reason for almost every technique in modern quantization research.

Turn on the outlier with a wide clip range, and watch the normal weights become coarser. Turn it off, or clip it, and the error becomes very small.

Per-channel scales

The direct fix is to use one scale for each output row, not one scale for the full tensor. Then an outlier makes only its own row worse.

Example — what the overhead actually costs
a 4096 × 4096 weight matrix = 16,777,216 weights per-tensor : 1 scale = 4 bytes of metadata per-channel : 4096 scales = 16,384 bytes → 0.1% overhead In the notebook's 64 × 128 test with one outlier, per-channel cuts RMSE by roughly 7.5x for 256 bytes on 8,192 weights (3% overhead).

You get a large gain in accuracy for almost no cost. That is why per-channel is the default everywhere. The production version of the same idea is LLM.int8(). It keeps a few outlier channels in fp16 and quantizes everything else.

Where quality actually breaks

The notebook sweeps bit-widths across the full model and measures validation loss. The shape of the result is consistent across models. Know it before you start to tune:

  • 8-bit costs almost nothing. In the notebook, the loss changes only in the fourth decimal place. That is why int8 inference is routine, not remarkable.
  • 4-bit per-channel has a real cost (0.05 nats in the notebook), but it is usable. Per-tensor at 4 bits costs approximately four times as much. Most quantized models that "run on a laptop" use 4-bit with small groups of weights that share a scale.
  • Below 4 bits, per-tensor quantization fails: at 3 bits it adds 1.1 nats. Per-channel lasts approximately one more bit (0.28 nats at 3 bits), and at 2 bits both schemes fail. The gap between the two schemes increases exactly where you need it most.
Fake quantization The notebook quantizes weights to integers and immediately changes them back to float. This measures the accuracy cost exactly, because it reproduces the numerical error. But it gives neither of the practical benefits, because the tensors and the arithmetic are still float32. To get real memory and speed savings, you need integer kernels that keep the weights packed (torch.ao.quantization, GGML, MLX). Fake quantization is the standard way to answer "is this worth doing?" before you do the engineering. Research papers report it.

LoRA

Fine-tuning calculates $W' = W + \Delta W$, where $\Delta W$ is a full-size matrix. LoRA assumes that $\Delta W$, the change that adapts a pretrained model, has a much lower intrinsic rank than $W$ itself. Thus it writes $\Delta W$ as a product of two thin matrices:

$$W' = W + \frac{\alpha}{r}BA \qquad B \in \mathbb{R}^{d\times r},\ A \in \mathbb{R}^{r\times d},\ r \ll d$$

Freeze $W$ completely. Train only $A$ and $B$.

Example — the parameter arithmetic
d = 4096, r = 8 full fine-tune : d² = 16,777,216 parameters per matrix LoRA : 2dr = 65,536 parameters per matrix 256x fewer and the optimizer state shrinks by the same factor: full : 16.8M × 12 bytes (grad + m + v) = 201 MB per matrix LoRA : 65k × 12 bytes = 786 KB per matrix

The second block is what really makes this fit in memory. LoRA removes 12 of the 16 bytes for each parameter. You must still store the weights themselves.

Three details that make it work

$B$ starts at zero. Thus $BA = 0$ at step 0, and the adapted model is exactly the base model. Fine-tuning starts from the pretrained behavior, not from a random change to it. A random change would discard part of what pretraining gave, before the first gradient step.

$A$ starts at random values. If both were zero, the gradient of each one would be proportional to the other, and both would stay zero forever. Exactly one of them can start at zero, and it must be the one on the output side.

The $\alpha/r$ scale keeps the update magnitude approximately constant when $r$ changes. Thus, when you change the rank, you do not have to tune the learning rate again.

Key concept The adapter is a separate, very small file. The base model never changes. Thus one copy of it serves each task, and to change the task you load a few megabytes, not a few gigabytes. That is why adapter-based deployment won. It turns "one fine-tuned model for each customer" from a storage problem into no problem.

The rank sweep, and what it tests

The main claim of LoRA comes from experiments, not from a proof. Thus test it. The notebook adapts a model trained on Carroll to Shakespeare at ranks 1, 2, 4, 8, 16 and 32. It measures the gain against the unadapted baseline of 2.499 nats:

Read that honestly. Rank 1, with three thousand parameters (0.37% of the model), already gets much more than half of the benefit. Rank 8 gets 85%, with a quarter of the parameters of rank 32. That strongly supports the low-rank hypothesis. If adaptation really needed a full-rank update, one direction would give almost nothing.

But the curve has not become flat. Rank 32 is clearly better than rank 8, and it shows no sign that it has stopped improving. The honest statement is steep diminishing returns, not saturation. You get most of the benefit cheaply, and you can continue to buy a little more without a limit. Where you stop is a budget decision. It is not a point where more rank stops helping.

Why this regime may flatter high ranks This is a 0.8M-parameter model, adapted for 500 steps between two very different authors. All three of those facts make it need more rank than a realistic setting. A small model has less redundant capacity to use again. A short run has not converged at any rank. A large domain shift is a bigger change than typical fine-tuning. Published results on large models become flat much earlier, because the base already contains most of what the target task needs. Treat the shape of this curve as real, and its exact position as specific to this experiment.

Catastrophic forgetting

The notebook measures something that is easy to skip. After adaptation to Shakespeare, the model is worse on Alice than it was. Adaptation to a new domain costs performance on the old one. This is not a defect specific to LoRA. Full fine-tuning forgets more.

But it is a strong argument to keep adapters as separate files that you can swap, and not to merge them permanently. If you merge, you trade one capability for another. If you keep them separate, you have both.

QLoRA: both at once

  1. Quantize the frozen base to 4 bits.
  2. Keep the LoRA adapters in full precision.
  3. Let gradients go through the quantized weights to the adapters.
Key concept — why quantizing a frozen base is safe Quantization error in a frozen base is a fixed bias. The model is only a slightly different, slightly worse fixed function. The adapters train on top of that function, and they can partly compensate for its errors. In a full fine-tune, the weights change at each step. Thus quantization error would come back at each step and interact with the optimizer state. It would accumulate, not stay in one place. Frozen-and-quantized is stable in a way that trainable-and-quantized is not. That asymmetry is the full reason that QLoRA works.

Nothing must backpropagate into the quantized values, only through them. At the scale of the notebook, the memory saving is very small. At 7B parameters, it is 28 GB against 3.5 GB. On the machine that this course targets, that is the difference between impossible and routine.

What actually runs you out of memory

Here is a result from the notebook that you should remember, because it is the opposite of what most people expect. For a 0.8M-parameter model, here is the activation memory at different sequence lengths. The model has 4 layers and 4 heads, and the batch is 64 sequences. Each head in each layer stores its own $L \times L$ attention matrix:

Sequence lengthHidden statesAttention matricesTotal
12817 MB67 MB84 MB
51267 MB1.07 GB1.14 GB

Hidden states increase linearly. Attention increases quadratically and becomes the largest part by far. At 4096 tokens, this 0.8-million-parameter model needs more memory than the full machine has. But the model itself is 3 MB. The parameter count has nothing to do with the memory problem.

That is why flash attention and sliding-window attention exist. (Flash attention tiles the calculation, so it never stores the $L \times L$ matrix.) For long-context work, they are more important than any weight-compression technique.

By hand — exercise 11.1 · quantize a vector
w = [0.10, −0.30, 0.80, −0.05, 0.45] Quantize symmetrically to 4 bits, so qmax = 2³ − 1 = 7.
  1. Calculate the scale $s$.
  2. Calculate $q$ for each weight. Round to the nearest integer.
  3. Dequantize, and calculate the error on each weight.
  4. Make sure that each error is at most $s/2$.
  5. Now add an outlier of 8.0, and calculate $s$ again. What is the new quantized value of the original 0.10? How much worse is its error?
Worked solution

1. $\max|w| = 0.80$, so $s = 0.80/7 = \mathbf{0.11429}$.

2 & 3.

w w/s q q·s error 0.10 0.875 1 0.1143 0.0143 −0.30 −2.625 −3 −0.3429 0.0429 0.80 7.000 7 0.8000 0.0000 −0.05 −0.437 0 0.0000 0.0500 0.45 3.937 4 0.4571 0.0071

4. $s/2 = 0.0571$, and the largest error is 0.0500 ✓. Note that $-0.05$ quantized to zero. At 4 bits, small weights disappear completely. With many such weights, this is a real loss of information. It is one reason that 4-bit needs per-channel scales to work at all.

5. With the outlier, $\max|w| = 8.0$ and $s = 8.0/7 = 1.1429$. That is ten times larger.

0.10 / 1.1429 = 0.0875 → rounds to q = 0 → ŵ = 0.0000 error = 0.10, up from 0.0143 — 7x worse and −0.30, 0.45 also collapse to 0. Four of the five original weights are now identically zero.

One unrelated weight destroyed the representation of each other weight. This is the outlier problem at its most extreme. It is exactly why per-channel scales (which would isolate the outlier in its own row) are not optional at low bit-widths.

By hand — exercise 11.2 · LoRA budgets

A transformer has 12 layers and $d_{\text{model}} = 768$. You adapt the four attention projections ($W^Q, W^K, W^V, W^O$) in each layer.

  1. How many parameters are in those projections in total?
  2. With LoRA at $r = 8$, how many parameters do you train? What percentage is that?
  3. Compare the optimizer memory (gradient + $m$ + $v$, 12 bytes for each trainable parameter) for full fine-tuning and for LoRA.
  4. You want to serve 50 customers, each with their own adapter. How much storage do 50 full fine-tunes need, and how much do 50 adapters need, at 4 bytes for each parameter? (Use 110M parameters for the full model.)
Worked solution

1. Each projection is $768 \times 768 = 589{,}824$. There are four in each layer, over 12 layers:

589,824 × 4 × 12 = 28,311,552 ≈ 28.3M parameters

2. Each LoRA pair is $2dr = 2(768)(8) = 12{,}288$:

12,288 × 4 × 12 = 589,824 trainable parameters 589,824 / 28,311,552 = 2.08% of the adapted projections 589,824 / 110,000,000 = 0.54% of the whole model

3.

full : 28.3M × 12 bytes = 340 MB LoRA : 0.59M × 12 bytes = 7 MB 48x less

Note that this is only the optimizer state. The frozen weights still use their 440 MB in fp32. QLoRA attacks that next.

4.

50 full fine-tunes : 50 × 110M × 4 bytes = 22.0 GB 50 LoRA adapters : 1 × 110M × 4 = 440 MB (shared base) + 50 × 0.59M × 4 = 118 MB = 558 MB 39x less

The practical difference is larger than the ratio shows. With adapters, the base model stays in memory, and a change of customer costs a 2.4 MB load. 50 full models cannot all be in memory at the same time, so each change is a 440 MB load. That is the real reason that adapter-based serving won.

By hand — exercise 11.3 · will it fit?

You need only multiplication. You have 17 GB of usable memory.

  1. Can you do a full fine-tune of a 1.5B-parameter model with Adam in fp32?
  2. Can you run inference on it in fp16?
  3. Can you do a LoRA fine-tune of it, with an fp16 frozen base and $r=8$ adapters on 1% of the weights? (Assume that activations add 30% of the size of the base weights.)
  4. Which single change gives the most: a 4-bit base, gradient checkpointing, or half the sequence length? State what you would need to know to answer correctly.
Worked solution

1. $1.5\text{B} \times 16 = \mathbf{24\text{ GB}}$ for weights, gradients and Adam state, before activations. No, and not by a small amount.

2. $1.5\text{B} \times 2 = 3\text{ GB}$ of weights, plus the KV cache and activations. That is approximately 3.5 GB. Yes, easily.

3.

frozen base fp16 : 1.5B × 2 = 3.00 GB LoRA weights : 15M × 4 = 0.06 GB LoRA grad + m + v : 15M × 12 = 0.18 GB activations (~30%) : = 0.90 GB ─────── 4.14 GB yes, easily

It goes from 24 GB (impossible) to 4.1 GB (routine), because you freeze the base and make the optimizer state smaller.

4. It depends on which term is largest. You cannot answer without the sequence length and the batch size. In part 3, the weights are largest, at 3.0 GB against 0.9 GB of activations. Thus 4-bit is the best single change (3.0 → 0.75 GB). But at a long sequence length, the attention matrices are larger than everything else. Remember the table above: a 3 MB model needed 69 GB of activations at 4096 tokens. There, half the sequence length gives a quadratic saving that nothing else can match. Measure before you optimize. The correct answer reverses, depending on a number that nobody has told you.

In the wild

You implemented both techniques from their definitions. Here are the same two ideas as one-line calls, and what each library adds to your version. 

# quantization — PyTorch native, CPU only, and you must pick a backend first
import torch.ao.quantization as tq
torch.backends.quantized.engine = 'qnnpack'   # 'none' by default on Apple silicon
qmodel = tq.quantize_dynamic(model, {nn.Linear}, dtype=torch.qint8)

# LoRA — the peft library, the de facto standard
from peft import LoraConfig, get_peft_model
model = get_peft_model(base, LoraConfig(
    r=8, lora_alpha=16, target_modules=["qkv", "proj"], lora_dropout=0.05))
model.print_trainable_parameters()   # your `trainable / total` line
model.save_pretrained("adapter/")    # a few MB, not a few GB

Here are three honest notes. We found all of them when we ran this code. First, torch.ao.quantization needs an explicit backend. On this build, the engine is 'none' by default. If you do not set it, the first quantized operation fails with NoQEngine, and that error does not clearly mean "select a backend". Second, the module is deprecated in current PyTorch, and the separate torchao package replaces it. Read its migration notes before you build on it.

Third, bitsandbytes is CUDA-first. It will not give you 4-bit kernels on Apple silicon at all. Here, MLX and llama.cpp/GGUF are what really work. The pattern in all three notes is the same lesson as the KV cache in Chapter 10: a technique that works is not necessarily a technique that works on your hardware. We built these by hand for a practical reason. When a 4-bit model becomes worse, the useful question is "which tensor has the outlier, and is my grid per-channel?". You cannot ask that question if quantization is only a flag that you passed.

Now do these on paper. Where you can, do them in your head. You can use a calculator for the logarithms. The goal is to know which number to use.

  1. You have a 16 GB laptop. Which of those four precisions fit the weights of a 7B model? What did you forget to include in the budget?
  2. LoRA at $r = 16$ on a $768 \times 768$ matrix. What fraction of the original is that? What fraction of the optimizer state?
  3. Why does the $B$ matrix of LoRA start at zero while $A$ is random? What would happen if both were random?
Answers

1. fp32 is not close. fp16 at 13.0 GiB fits on paper, but it is a trap. It leaves approximately 3 GB for the operating system, your editor and all the activations. In practice, it will not run. int8 at 6.5 GiB and int4 at 3.3 GiB are the two that really work. You forgot: activations, the KV cache (which increases with context and batch), gradients and optimizer states if you train, and fragmentation, which makes the practical limit lower than the arithmetic limit. The measurement in this chapter shows that sequence length, not parameter count, is usually what really uses all the budget.

2. $2 \times 16 \times 768 = 24{,}576$ against $768^2 = 589{,}824$, so 4.17%. But the saving in optimizer state is larger. Adam keeps two moments for each trainable parameter. Thus, when you freeze the base model, you also remove approximately 96% of that state. That is why LoRA decreases memory much more than the parameter fraction suggests.

3. So that $BA = 0$ at step 0, and the adapted model is exactly the base model. Thus training starts from the pretrained function, not from a random change to it. If both were random, the adapter would add noise to each layer before it learned anything. That is exactly the damage that fine-tuning must prevent. If both were zero, it would be even worse. The gradient to $A$ is proportional to $B$, so nothing would ever move.

The habit. Before you ask whether a model is good enough, find out whether it fits. Bytes for each parameter times the parameter count is thirty seconds of arithmetic. It rules out most proposals immediately.

Say it backRecommended

Explain this to your favorite LLM, in your own words: quantization and LoRA both make a model cheaper. What is each one actually trading away, and why do they compose? Then ask it to correct you. Ask it to question each part where you were vague, not only the parts where you were wrong, because the gaps are in the vague parts.

What a good answer covers — open this afterwards, not before
  1. Quantization gives up precision. It stores the same parameters in fewer bits, and it accepts the rounding error that results.
  2. LoRA gives up expressiveness. It freezes the parameters and learns a low-rank correction. Thus the model can make only changes inside that subspace.
  3. Thus one decreases the cost of having the weights, and the other decreases the cost of changing them. These are different budgets, and that is why they stack.
  4. QLoRA keeps a quantized frozen base and trains full-precision adapters on top. Thus the optimizer never accumulates the rounding error.
  5. Both assume that the part that they discard (low-order bits, high-rank directions) carried little of what was important. Both assumptions come from experiments. Neither is guaranteed.

Most common miss. An answer describes both as "making the model smaller". They decrease different quantities. If an explanation does not separate storage from adaptation, it cannot explain why the combination helps.
