PyTorch in Practice

Everything so far has been architecture. This chapter is craft: the patterns that separate code that trains from code that trains reliably, reproducibly, and fast enough to iterate on. None of it is conceptually hard, and all of it is the difference between a working project and a week of confusion.

Factor the training loop

Inline training loops are fine for one experiment and unmanageable by the fifth. Two functions cover almost every project: 

def train_one_epoch(model, loader, criterion, optimizer, device):
    model.train()
    total = 0.0
    for xb, yb in loader:
        xb, yb = xb.to(device), yb.to(device)
        optimizer.zero_grad()
        loss = criterion(model(xb), yb)
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        total += loss.item() * xb.size(0)
    return total / len(loader.dataset)


@torch.no_grad()
def evaluate(model, loader, criterion, device):
    model.eval()
    total = 0.0
    for xb, yb in loader:
        xb, yb = xb.to(device), yb.to(device)
        total += criterion(model(xb), yb).item() * xb.size(0)
    return total / len(loader.dataset)

Three details in there are worth calling out.

loss.item() * xb.size(0) divided by len(dataset) weights each batch by its true size. Averaging batch means directly over-weights the final partial batch — a small error, but it makes your reported loss depend on your batch size, which is a bad property for a number you compare across runs.

.item() is essential, not cosmetic. Accumulating the tensor itself keeps the entire computational graph alive for every batch in the epoch, and you will run out of memory with no obvious cause. .item() extracts a Python float and drops the graph.

@torch.no_grad() as a decorator applies to the whole function — cleaner than wrapping the body, and impossible to forget halfway through.

Learning rate schedules

A constant learning rate is a compromise: too large to settle at the end, too small to make progress at the start. Schedules resolve it.

Warmup ramps the rate up over the first few hundred steps. The reason is specific to Adam: its second-moment estimate $v$ is computed from a handful of samples early on and is correspondingly unreliable, so a full-size step divided by a bad $\sqrt{v}$ can be enormous. Transformers are notoriously sensitive to this — training one without warmup often diverges in the first hundred steps.

Cosine decay then anneals smoothly to near zero, spending the end of training taking small careful steps near a minimum instead of bouncing around it. Warmup plus cosine is the default for essentially every modern language model.

ReduceLROnPlateau, which Chapter 09 uses, is the reactive alternative: halve the rate whenever validation loss stops improving. It requires no knowledge of total training length, which makes it convenient for exploratory work.

Step the scheduler once per epoch or once per batch — decide which Most schedulers advance on scheduler.step(). Warmup schedules are per-batch; ReduceLROnPlateau is per-epoch and takes the validation metric as an argument. Mixing them up gives you a schedule that completes in the first epoch, or one that never moves. Print the learning rate for the first few epochs — always.

Checkpointing

torch.save({
    'epoch': epoch,
    'model_state_dict': model.state_dict(),
    'optimizer_state_dict': optimizer.state_dict(),
    'best_val': best_val,
}, 'checkpoint.pt')

Save the state_dict, not the model object. Pickling the object embeds your class definitions and import paths, so the file breaks the moment you rename a module. A state_dict is just a dictionary of tensors and loads into any code that defines a matching architecture.

Save the optimizer too. Adam's $m$ and $v$ accumulate real information, and resuming without them restarts the moment estimates from zero — visible as a loss spike right after every resume.

And keep the best checkpoint, not the last: 

if val_loss < best_val:
    best_val, best_state = val_loss, copy.deepcopy(model.state_dict())
...
model.load_state_dict(best_state)

Validation loss frequently turns upward long before training ends. Chapter 09 hits its best validation loss at epoch 11 of 30 and is meaningfully worse by epoch 30 — without this pattern, you would ship the worse model. copy.deepcopy matters: state_dict() returns references to live tensors, so keeping it without copying keeps a handle on weights that keep changing.

Batching sequences without wasting compute

Padding every sequence to a global maximum is simple and expensive.

Tick sort batch by length. Grouping similar-length sequences means each batch pads only to its own maximum rather than to the longest sequence in the dataset. The saving is larger than the bar chart suggests, because attention is quadratic in padded length: cutting padded length by 30% cuts attention cost by about half.

The general form is a bucketing sampler — sort by length, chunk into batches, shuffle the batch order (so you keep randomness between epochs without breaking the length grouping). Combine it with a custom collate_fn that pads dynamically per batch rather than pre-padding the whole dataset.

DataLoader settings on a Mac num_workers>0 spawns subprocesses for data loading. On macOS the default start method is spawn, so each worker re-imports your module — anything at module scope runs again in every worker. Keep heavy setup inside if __name__ == "__main__": or inside functions. In notebooks, num_workers=0 is often genuinely fastest, since the datasets here are small and already in memory. pin_memory=True helps CUDA transfers and does nothing useful on MPS.

Reproducibility

torch.manual_seed(42)
np.random.seed(42)
random.seed(42)

Necessary, and not sufficient. GPU reduction kernels accumulate in nondeterministic order, so floating-point results differ slightly run to run; torch.use_deterministic_algorithms(True) forces deterministic kernels where they exist and raises an error where they do not. Dataloader workers need worker_init_fn to seed each subprocess distinctly.

The deeper point is that a single run tells you less than people assume. Different seeds on the same code routinely differ by a point or two of accuracy on small datasets. If a change improves your model by half a point, you have measured noise. Run three seeds before believing anything.

Key concept — the single best debugging move Before training on the full dataset, take eight examples and overfit them completely. Turn off dropout and regularisation and train until the loss is essentially zero. If you cannot drive the loss to zero on eight examples, the bug is in your model, loss, or data pipeline — not in your hyperparameters — and no amount of tuning on the full dataset will find it. This takes two minutes and saves entire afternoons.

Making it fast on Apple silicon

Unified memory is the M4's defining feature: CPU and GPU share one pool, so .to('mps') costs far less than a PCIe transfer to a discrete GPU. It also means your model competes with everything else on the machine for the same 24 GB, and there is no separate VRAM figure to watch.

  • Measure before optimising. MPS is asynchronous, so wall-clock timing around a forward pass measures only queueing. Call torch.mps.synchronize() before stopping the clock.
  • Batch size is the first lever. Small models are launch-overhead-bound; going from batch 16 to 128 is often nearly free in time and a large gain in throughput.
  • Watch for silent CPU fallback. With PYTORCH_ENABLE_MPS_FALLBACK=1, unsupported ops run on CPU — correct, but each one forces a synchronisation. One fallback op inside your inner loop can cost more than everything else combined.
  • torch.compile is not the answer here. Its MPS support lags CUDA considerably; on these model sizes it usually costs more in compile time than it returns.
  • float16 halves memory and is well supported on MPS, but Apple's backend lacks the mature autocast/GradScaler story CUDA has. Use it for inference freely; for training, treat it as an experiment (see Chapter 11).
By hand — exercise 08.1

Memory arithmetic for a training run — the calculation you should do before starting one.

model: 12M parameters, fp32, trained with Adam batch: 64 sequences × 512 tokens activations: measured at ~1.2 KB per token per layer, 6 layers
  1. Memory for weights, gradients, and Adam's two state tensors.
  2. Memory for activations retained for the backward pass.
  3. Total, and how it compares to a 24 GB budget (assume ~17 GB usable).
  4. You need to double the batch size and cannot. Give three ways to get the effect, and state what each one costs.
Worked solution

1. 12M parameters × 4 bytes = 48 MB each for weights, gradients, Adam $m$, and Adam $v$ = 192 MB, i.e. 16 bytes per parameter.

2. $64 \times 512 \times 1.2\text{ KB} \times 6 = \mathbf{236\text{ MB}}$.

3. About 428 MB plus framework overhead — comfortably inside 17 GB. Worth noticing which term dominates: activations exceed the entire model, and they scale with batch size and sequence length while the model does not. On small models, activations are the thing that actually runs you out of memory.

4.

  • Gradient accumulation — run two batches of 64, calling backward() on each and step() only after the second. Gradients accumulate by default (Chapter 02), so this is mathematically identical to batch 128. Costs: two forward/backward passes of wall-clock time, and you must scale the loss by 1/2 to keep the gradient magnitude right.
  • Gradient checkpointing — store only some activations and recompute the rest during the backward pass. Cuts activation memory by roughly $\sqrt{N}$ for $N$ layers. Costs about 30% extra compute.
  • Shorter sequences — halve the sequence length. Costs the model any dependency longer than the new window, and for attention it is a quadratic saving, so it is the most effective of the three per unit of harm.

Reading a training log. Diagnose each, and name the first thing you would change.

Run A Run B Run C Run D ep tr val tr val tr val tr val 1 2.31 2.30 2.30 2.29 2.31 2.28 4.02 3.81 5 2.30 2.30 1.41 1.52 0.98 1.61 nan nan 10 2.30 2.31 0.88 1.19 0.31 2.04 - - 15 2.30 2.30 0.71 1.14 0.09 2.55 - -
Worked solution

Run A — not learning at all. The loss sits at 2.30, which for a 10-class problem is exactly $\ln 10 = 2.303$: the model is outputting a uniform distribution and never moving. Nothing is reaching the weights. Check for a missing zero_grad(), a learning rate of zero, parameters not passed to the optimizer, or a requires_grad=False left somewhere. First move: print p.grad.norm() after backward() — if it is zero or None, you have found it.

Run B — healthy. Both losses fall, with a modest and stable gap (0.71 vs 1.14) that is normal generalisation error. Validation is still improving at epoch 15. First move: keep training, and consider a larger model.

Run C — textbook overfitting. Validation bottoms out around epoch 5 at 1.61 and then climbs steadily while training loss drives towards zero. The model is memorising. First move: restore the epoch-5 weights, then add regularisation — dropout, weight decay, more data, or less capacity. Note that without best-checkpoint restore you would have shipped the epoch-15 model at val 2.55, which is worse than the model was after five epochs.

Run D — divergence. Starting loss of 4.02 is already high and it reaches nan within five epochs. Almost always too large a learning rate; occasionally a $\log 0$ or an all-masked attention row. First move: cut the learning rate by 10× and add clip_grad_norm_. If it still diverges, print the loss every batch rather than every epoch to find the exact step where it breaks.
