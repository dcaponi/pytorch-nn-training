Appendix

This appendix collects reference material in one place: notation, tensor-shape conventions, a glossary, and the failures that you will really see. After that, three sections look past the end of the course. From scratch to the library maps each component that you built by hand to its production equivalent. Reading the literature shows how to find the real contribution of a paper. The modern stack covers the approximately eight changes between the transformer of Chapter 08 and a current frontier model. You can read all of them with the mathematics that you now have.

Making it fast on Apple silicon

Unified memory is the defining feature of Apple Silicon. The CPU and the GPU share one pool. Thus .to('mps') costs much less than a PCIe transfer to a discrete GPU. But it also means that your model shares the same pool with the operating system and everything else. There is no separate VRAM value to watch. A discrete NVIDIA card gives you a fixed budget that is only yours, and it tells you when you go over it.

  • Measure before you optimize. MPS is asynchronous. Thus, if you time a forward pass with a clock, you measure only the queueing. Call torch.mps.synchronize() before you stop the clock.
  • Batch size is the first control. Small models are limited by launch overhead. A change from batch 16 to 128 frequently costs almost no time and gives a large gain in throughput.
  • Watch for silent CPU fallback. With PYTORCH_ENABLE_MPS_FALLBACK=1, operations without MPS support run on the CPU. The result is correct, but each one forces a synchronization. One fallback operation in your inner loop can cost more than everything else together.
  • torch.compile is not the answer here. Its MPS support is much less mature than its CUDA support. At these model sizes, it usually costs more in compile time than it gives back.
  • float16 halves memory, and MPS supports it well. But the Apple backend does not have the mature autocast and GradScaler support that CUDA has. Use float16 freely for inference. For training, treat it as an experiment (see Chapter 11).

The output-size formula

$$L_{\text{out}} = \left\lfloor\frac{L_{\text{in}} + 2p - k}{s}\right\rfloor + 1$$

Here $p$ is the padding, $k$ is the kernel size and $s$ is the stride. With $p = 0$ and $s = 1$, it is $L - k + 1$. Set $p = (k-1)/2$ with an odd $k$ and $s = 1$, and the length stays exactly the same. This is "same" padding.

Apple silicon notes

These notes are specific to Apple Silicon. They apply when PyTorch selects the Metal backend, which each notebook does automatically on an M-series Mac. If you use CUDA or the CPU, this section does not apply to you, and nothing in the course changes. We lost time to find each one.

MPS silently returns zeros for out-of-range embedding indices

This is the most dangerous problem in the backend. It caused a real bug while we wrote Chapter 10. Cached generation went past block_size, so the code used an index for pos_emb that was out of range. 

e = nn.Embedding(128, 8)
e(torch.tensor([200]))                            # cpu : IndexError
e.to('mps')(torch.tensor([200], device='mps'))    # mps : a row of zeros

The model continued to run with a zero position embedding. It gave fluent text for a hundred tokens, and then it changed to noise. There was no error and no warning. Nothing showed in the loss, because it occurs at inference time. When the MPS output looks wrong but the CPU output does not, run it again on the CPU. That is the fastest way to change a silent corruption into a stack trace.

  • nn.LSTM dropout is broken. With dropout>0, a stacked nn.LSTM on MPS does not apply random dropout and fails to train (PyTorch 2.12). nn.RNN and nn.GRU are not affected. Train that model on the CPU, or set dropout=0. See Chapter 05.
  • float64 has no support. A dtype=torch.float64 fails when you move it to MPS. Use float32 by default.
  • Quantization needs an explicit engine. torch.backends.quantized.engine is 'none' by default here. Thus quantize_dynamic fails with Didn't find engine for operation quantized::linear_prepack NoQEngine until you set it to 'qnnpack'. That is the one backend that this platform supports. Note also that torch.ao.quantization is deprecated, and the separate torchao package replaces it.
  • The FlashAttention backend is CUDA-only. F.scaled_dot_product_attention is still the correct call. It is correct, and it is never much slower. But on MPS, it uses a math or memory-efficient fallback, not a flash kernel. Thus do not expect the published speedups. The notebook of Chapter 10 measures this: the fused path is not measurably faster here, but the memory argument is true on each backend. Keep the general habit. When a library advertises a speedup, check that the fast path exists on your hardware before you give it credit.
  • Time it correctly. MPS is asynchronous. Thus, if you time a forward pass with a clock, you measure the queueing, not the work. Call torch.mps.synchronize() before you stop the clock.
  • MPS can be slower than the CPU on very small models. With only a few examples, the overhead to launch each kernel is larger than the work. The benefit starts at Chapter 03.
  • Watch for silent CPU fallback. With PYTORCH_ENABLE_MPS_FALLBACK=1, an operation without MPS support runs on the CPU. The result is correct, but each occurrence forces a synchronization. One such operation in an inner loop can cost more than everything else together.
  • num_workers=0 is frequently fastest in notebooks. macOS spawns workers and does not fork them. Thus each worker imports your module again.
  • pin_memory=True does nothing useful on unified memory.
  • torch.compile is not worth it here. Its MPS support is less mature than its CUDA support. At these model sizes, it usually costs more in compile time than it gives back.

Reading the literature

You did the mathematics by hand so that papers become readable. Most machine-learning papers are short. Usually, the contribution is one equation, with experiments around it. Here is how to find it.

A reading order

  1. Read the abstract, then the figures, then the conclusions. The figures usually carry the real claim. After this, if you cannot state the claim in one sentence, the paper may not be worth a full reading.
  2. Find the one equation. Almost each architecture paper has one new expression. You already know the rest. Find that expression, and write its shapes. If the shapes do not combine, you read it wrong. That occurs more frequently than a wrong paper.
  3. Ask what resource it saves. Almost each modern contribution trades one of these: parameters, activation memory, KV-cache memory, FLOPs per token, wall-clock time or data. When you name which one, that usually explains the full design.
  4. Read the ablations before the main table. The main table compares with the models of other people, and scale and data confound it. The ablation compares with the authors' own model with one thing removed. That is the only controlled comparison in the paper.
  5. Check what the paper does not report. Missing seeds, missing error bars, a baseline that got less tuning than the method, and evaluation on the set used for model selection are all common. Each one decides whether you can trust the result.
Key concept — the shape check

When the notation is too difficult, change it to shapes. Different authors use different notation, but tensor shapes are always the same. "Project the input to a latent of dimension $d_c$, then up-project per head" is ambiguous as prose. When you write it as (B, L, d) → (B, L, d_c) → (B, H, L, d_h), it is clear.

Then count the parameters and the memory for each shape. If the paper claims a saving, your count must give the same saving. If it does not, you read the method wrong, or you found something worth a question. Both results are useful, and the second is how people build reputations.

The modern stack: what changed after 2017

The transformer of Chapter 08 is the 2017 design. A current frontier model is clearly the same block, with approximately eight changes. Each change is a small idea that is easy to read. When you know all eight, you have most of what separates "can implement a transformer" from "can read the technical report of a frontier model and implement it again".

Each entry below gives what it replaces, the idea, and the resource that it gets back. None of them needs mathematics past Chapter 00.

Normalization: LayerNorm → RMSNorm

$$\operatorname{RMSNorm}(x) = \frac{x}{\sqrt{\frac{1}{d}\sum_i x_i^2 + \epsilon}}\odot\gamma$$

Remove the mean subtraction and the $\beta$ shift. Keep only the scale. In experiments, the re-centering gives little, and its removal saves one pass over the features and one set of parameters. Gets back: wall-clock time, a little. Llama, Mistral, DeepSeek and almost all current models use it.

Activation: ReLU → SwiGLU

$$\operatorname{SwiGLU}(x) = \big(\operatorname{Swish}(xW_1) \odot xV\big)W_2 \qquad \operatorname{Swish}(z) = z\,\sigma(z)$$

This is a gated feed-forward block. One projection makes the content. A second projection makes a multiplicative gate, exactly as an LSTM gate does. It needs three weight matrices, not two. Thus implementations decrease the hidden width to $\tfrac{2}{3}\cdot 4d$ to keep the parameter count fixed. It is consistently better for each parameter. Gets back: quality at equal size.

Position: learned/sinusoidal → RoPE

Do not add a position vector to the embedding. Rotate $q$ and $k$ by an angle proportional to position, in 2-D pairs of dimensions. A dot product depends only on the relative angle. Thus $q_m \cdot k_n$ depends on $m - n$, not on $m$ and $n$ separately. You get relative position at no cost, inside the attention operation.

This directly fixes the hard context limit from Chapter 10. There is no position-embedding table to run out of. Also, if you interpolate or rescale the frequencies, you can extend the context of a model that is already trained. Gets back: length generalization.

KV cache: MHA → GQA/MQA → latent attention

Chapter 10 showed that the KV cache limits the number of concurrent users. Here are three attacks on it, one after the other:

  • Multi-query attention (MQA): all heads share one key head and one value head. The cache becomes $H$ times smaller. Quality decreases a little.
  • Grouped-query attention (GQA): heads share keys and values in groups, for example of 8. This gives most of the saving and almost none of the loss. It is the current default.
  • Multi-head latent attention (MLA), from DeepSeek-V2: compress keys and values into a low-rank latent vector, and cache that. The model makes the projections for each head again when it needs them. It is the low-rank factorization of Chapter 11, applied to the cache and not to the weights. It is a good example of an idea that you already know, moved to a new place.

Gets back: KV-cache memory, which means serving throughput.

Capacity: dense → mixture of experts

Replace the feed-forward block with $N$ expert blocks and a router. The router sends each token to the top-$k$ experts (usually $k = 1$ or 2). The total parameters increase by approximately $N$. The active parameters for each token do not. A model can hold much more knowledge than it spends compute on at any one token.

The engineering problem is load balance. If you do not control it, a router sends almost all tokens to a few experts. Classic MoE adds an auxiliary loss for balance, and that loss competes with the language modeling objective. DeepSeek-V3 adjusts a routing bias for each expert, based on the load that it measures. This gets balance without an auxiliary loss term. DeepSeekMoE also divides the experts more finely, and it keeps a few shared experts always on for common patterns. Gets back: knowledge per FLOP.

Attention kernels: FlashAttention

This is not a modeling change at all. The mathematics is the same, but the kernel calculates it in tiles with an online softmax. Thus it never writes the (B, H, L, L) matrix to memory, and memory becomes linear in $L$, not quadratic. Gets back: context length. Remember this lesson about the field. One of the largest capability increases of the last several years came from a new kernel, not from a new architecture.

Decoding: speculative and multi-token

Generation is sequential and limited by memory bandwidth, so the GPU is mostly idle. Speculative decoding uses a small draft model to propose several tokens. Then the large model verifies them in one parallel pass, and it accepts the longest correct prefix. The output distribution is provably the same, and it is several times faster. DeepSeek-V3 puts a related idea into training with a multi-token prediction objective. It predicts more than one future token at each position. Gets back: tokens per second.

Post-training: SFT, then preference optimization

A base model trained as in Chapter 10 continues text. It does not follow instructions. A separate stage changes it into an assistant. First comes supervised fine-tuning on demonstrations. Then comes optimization against preferences: RLHF/PPO in the classic form, DPO without a reward model, and GRPO for reasoning training. (GRPO is the DeepSeek variant. It removes the value network and normalizes advantages within a group of sampled responses.) DeepSeek-R1 is an important demonstration. It shows that reasoning behavior can come from reinforcement learning against answers that you can verify, with little or no supervised start. Gets back: usefulness, which pretraining does not give.

Key concept — the shape of progress Look at that list, and see how few entries are new mathematics. Two are factorizations that you already implemented (the low rank of LoRA, used again for the KV cache). Two are gating (SwiGLU and MoE routing), which is the LSTM idea from Chapter 05. One is a new kernel, one is a rotation, and one is a change of training objective. You can get to the frontier from here. What separates you from it is not mathematics that you have not seen. It is engineering scale, data, and the habit of asking which resource a design gets back.

Making work others will trust

The technical ability to build these systems is one skill. The ability to make someone believe a result is a different skill, and it is less common. Most of it comes from a few habits. They all occur in other places in this book. Here they are together.

HabitWhy it persuades
Report a spread, never a single numberseed variance often exceeds the effect being claimed (exercise 00.17)
Compare at matched parameters and matched computeotherwise you have measured capacity, not your idea
Tune the baseline as hard as the methodan undertuned baseline is the most common way good-faith work becomes wrong
Ablate one thing at a timethe ablation is the only controlled comparison you will have
Touch the test set oncerepeated selection is overfitting in slow motion
State what you cannot concludereaders who spot an unstated limitation stop trusting the stated ones
Publish the code and the seedsreproducibility is the cheapest credibility available
Show a failure casea method with no reported failure mode reads as unexamined

Before you publish anything, in a paper, a blog post or a pull request, do this test. Suppose that a hostile reader with your data and code tried to break this claim. What would they attack first? Answer that in the text. It is the paragraph with the highest return that you can write. It changes your most probable critic into a reader who trusts the rest.

About this book

book/build.py builds the book from HTML fragments in book/chapters/, one for each chapter. It uses only the standard library. It concatenates the fragments, gives stable anchors to the headings, checks each cross-reference, and highlights the code blocks. A vendored copy of KaTeX renders the mathematics, so nothing here needs a network connection. The interactive figures are canvas widgets, written by hand in book/book.js. Each one calculates the same arithmetic as the text next to it. Nothing is drawn only to look convincing. 

python3 book/build.py           # rebuild book/index.html
python3 book/build.py --check   # validate fragments and cross-references only

To add or edit a chapter, change a file in book/chapters/ and build again. The filenames sort into reading sequence. Each fragment is one <section class="chapter" id="…"> with an <h1>. Headings without an explicit id get a generated id that comes from the heading text. Thus, if you change the text of a heading, update the cross-references that point to it, or give the heading an explicit id. build.py --check finds each reference that breaks.
