Text, Embeddings, and a Baseline

This chapter uses two thousand real film reviews. It is the first model in this book that uses data that it did not invent. Three things must happen before any architecture can work. Text becomes integers. Integers become vectors that the model owns and changes. A batch becomes a rectangle. Then we build the simplest classifier that works. A number that you plan to beat is worth more than a number that you cannot compare with anything.

From words to numbers

A network takes vectors of floats. A review is a list of words. Three steps connect the two. Each step is a design decision with results.

Tokenize. Split the text into units. Here we use lowercase tokens from NLTK, split at whitespace and punctuation. This is simple, but it makes "Don't" and "dont" different words, and that is a real cost. Chapter 10 introduces subword tokenization, which fixes this correctly.

Build a vocabulary. Map the $V$ most frequent tokens to integer indices. Keep index 0 for <PAD> and index 1 for <UNK>. Each token outside the top $V$ becomes <UNK>. Vocabulary size is a balance between coverage and parameters. The embedding table alone has $V \times d$ numbers. At $V = 10{,}000$ and $d = 64$, as in the notebook, that is 640,000 parameters before the real model starts.

Pad or truncate to a fixed length. Tensors are rectangular, but reviews are not. Each sequence becomes exactly $L$ tokens. If it is longer, we cut it. If it is shorter, we fill it with <PAD>. This looks like only bookkeeping, but it is not. The section on batching shows how much compute the padding wastes. The box below shows what the truncation costs in accuracy.

Leakage Build the vocabulary from the training split only. If you build it from the full corpus, the test-set vocabulary affects the model. This makes your reported accuracy too high, and you do not see it. In NLP, this is the most common way to give yourself a false result. The symptom is very good test numbers that fail on really new data, and you see it much too late.

Eighteen points of accuracy depend on a variable that most people set one time and never examine again. The reason is specific to averaging. A mean gives each token the same weight. Thus, if you cut three quarters of a review, you remove three quarters of the evidence. A model that pooled with a maximum would almost not notice. It needs only the single most decisive phrase to stay after the cut. Before you tune anything, check what your preprocessing discarded. Here, it is a larger effect than any model choice in this chapter.

Embeddings: geometry learned from the task

One-hot vectors are the obvious encoding, and a bad one. Each is a 10,000-dimensional vector with all zeros except one 1. In that encoding, each pair of words is at exactly the same distance. "Excellent" is as far from "superb" as it is from "the". There is no structure for the model to use.

An embedding replaces this with a dense, learned vector, usually of 50 to 300 numbers. nn.Embedding(V, d) is a $V \times d$ lookup table: 

emb = nn.Embedding(vocab_size, 100, padding_idx=0)
x = emb(token_ids)      # (B, L) -> (B, L, 100)
Key concept An embedding layer is a linear layer applied to a one-hot vector. When you multiply a one-hot vector by a matrix, you select one row. The library uses a lookup, because the multiplication would be a waste. But this equivalence is why gradients go through it normally. The backward pass sends gradient into the rows that the batch used, and it does not touch the other rows. Words that are not in a batch get no update.
Example — a lookup is a matrix multiply

Here is a vocabulary of 4 words with 3-dimensional embeddings:

E (4×3) one-hot for "good" (index 2) the [ 0.1, 0.0, −0.2 ] h = [0, 0, 1, 0] a [ 0.3, −0.1, 0.1 ] good [ 0.9, 0.8, −0.5 ] h @ E = 0·row0 + 0·row1 + 1·row2 + 0·row3 bad [−0.8, −0.7, 0.6 ] = [0.9, 0.8, −0.5] which is exactly E[2] — the lookup, with 9 pointless multiplications.

The equivalence also explains the backward pass. $h$ selects one row. Thus the gradient $h^\top\delta$ is zero at all rows except row 2, which gets $\delta$. Only the words in the batch get an update. If a word occurs three times in a batch, it gets three contributions that add together, exactly as the sum over paths requires.

Gradient descent on this task trains the vectors. Thus they arrange themselves according to what this task needs. Train on sentiment, and "boring", "tedious" and "dull" move near each other. The model does not know that they are synonyms. They move together because they predict the same label. padding_idx=0 keeps the pad row at zero and gives it no updates. Thus padding adds nothing.

Averaging: the simplest thing that works

The embedding layer changes a review into a matrix: one row for each token, $L$ rows of $d$ numbers. A classifier needs one vector. The cheapest possible connection is the average of the rows: 

x = self.embedding(ids)          # (B, L, d)
x = x.mean(dim=1)                # (B, d)      one vector per review
return self.fc(x)                # (B, 1)      one score per review

That is the full model. Its name is a bag of embeddings. Take it seriously, for two reasons. First, on sentiment it is really difficult to beat, because most reviews are decided by which words occur, not by their arrangement. Second, we will compare each more advanced model in this book with it.

Average over the real tokens, not the padding x.mean(dim=1) averages over all $L$ positions. That includes each <PAD> that you added to make the batch rectangular. A 40-token review padded to 200 gets 80% of its average from padding. Short reviews get more damage than long ones. Thus the bug does not only add noise. It adds noise that correlates with length. To fix it, multiply by the mask, sum, and divide by the true length: 
mask = (ids != PAD_IDX).unsqueeze(-1)        # (B, L, 1)
x = (x * mask).sum(1) / mask.sum(1)          # (B, d)
The unsqueeze is the broadcasting fix from Chapter 00. The pooling layer of the transformer makes the same type of error later if you are not careful.
Key concept Averaging discards the word order completely. "The acting saved a terrible script" and "a terrible script saved the acting" contain the same words. Thus they give the same vector, and the model cannot tell them apart, even in principle. You cannot tune this weakness away. It is a property of the architecture, and it puts a hard limit on this model that no quantity of data will remove. Each chapter from Chapter 04 on gives a different answer to one question: how do you keep the order?

Batching without wasting compute

If you pad each sequence to one global maximum, the code is simple, but it is expensive.

Select sort batch by length. When you group sequences of similar length, each batch pads only to its own maximum, not to the longest sequence in the dataset. The saving is larger than the bar chart shows, because the cost of attention is quadratic in the padded length. If you cut the padded length by 30%, you cut the cost of attention by approximately half.

The general form is a bucketing sampler. It sorts by length, divides the data into batches, and shuffles the sequence of the batches. Thus you keep randomness between epochs, and you keep the grouping by length. Use it with a custom collate_fn that pads each batch dynamically. Do not pad the full dataset in advance.

DataLoader settings on a Mac num_workers>0 starts subprocesses to load data. On macOS, the default start method is spawn, so each worker imports your module again. Anything at module scope runs again in each worker. Keep heavy setup inside if __name__ == "__main__": or inside functions. In notebooks, num_workers=0 is frequently the fastest, because the datasets here are small and already in memory. pin_memory=True helps CUDA transfers, and it does nothing useful on MPS.

Dropout

Two thousand reviews and a model with more than a million parameters will cause memorization. Dropout prevents this. During training, it sets each activation to zero independently with probability $p$. It multiplies the activations that stay by $1/(1-p)$, so the expected sum does not change.

The usual explanation is that this prevents co-adaptation. No unit can depend on a specific partner, so each feature must be useful alone. A second explanation is that dropout trains a very large ensemble of subnetworks that share weights, and averages them at test time. Both explanations are correct. Both give the same practical rule: dropout must be off at evaluation. model.eval() does that. If you forget it, your test numbers are noisy, too low and not reproducible.

Batching and the train/test split

Dataset tells PyTorch how to get one example. DataLoader does batching, shuffling and parallel loading. Shuffling is more important than it looks. The movie review corpus is sorted by label. Thus a loader without shuffle gives 1,000 negative reviews and then 1,000 positive ones. The model would learn "always negative", and then lose all of it.

The held-out test set is the only honest number that you have. Training accuracy measures memorization. Test accuracy measures learning. A gap of a few points is normal. A large gap that increases is the definition of overfitting. Chapter 09 has exactly this problem. It solves it with the weights from the best validation epoch.

By hand — exercise 03.1 · what averaging keeps and what it losesMust do

Use a one-dimensional embedding. Each token is one number, and the full model fits on a line. Positive numbers lean positive.

sentence: the film was not bad at all embedding: 0.1 0.3 0.0 -0.9 -0.6 0.1 0.0 the classifier predicts POSITIVE when the pooled value is above 0
  1. Calculate the mean over the seven tokens. What does the model predict?
  2. The sentence means that the film was good. Which word causes the wrong prediction? Why can no choice of embedding values fix it while the pooling is an average?
  3. Shuffle the tokens into "bad the not all was film at", and calculate the mean again. What does this tell you about what the model can represent?
  4. Now pad the sentence to length 10 with three <PAD> tokens that have embedding 0.0. Average over all ten positions. How much is the result wrong, and in which direction?
Worked solution

1. The sum of the values is $-1.0$. Thus the mean is $-1.0/7 = \mathbf{-0.143}$, and the model predicts negative.

2. not, at $-0.9$. The phrase "not bad at all" is positive because not inverts the words after it. But averaging cannot represent "inverts the words after it". It can only represent "adds its own number". You could move not to $+0.9$ and get this sentence correct. But then "not good" would also be positive. The failure is in the structure. Tuning cannot fix it. One number for each token, combined by addition, has no place for a rule about neighbors.

3. The same: $-0.143$. Addition is commutative, so each sequence of the same tokens gives the same vector. The model is not bad at word order. It cannot see word order at all. That is a stronger and more useful fact.

4. $-1.0/10 = \mathbf{-0.100}$. Padding moves it 30% toward zero, which means "no opinion". Note the direction. Padding always moves the average toward the embedding of <PAD>. It moves a short review more than a long one. A model trained this way learns that short reviews have weaker opinions. That is a fact about your padding, not about films.

By hand — exercise 03.2 · where the parameters actually areRecommended

Count the parameters for the model in the notebook. You need only multiplication.

vocab V = 10,000 embedding d = 64 sequence length L = 600 model: Embedding(V, d) -> masked mean over L -> Linear(d, 1)
  1. Count the parameters in the embedding table.
  2. Count the parameters in the pooling step.
  3. Count the parameters in the final linear layer.
  4. Calculate the total, and the fraction in the embedding. What does that tell you about the source of overfitting? Where would tuning be a waste?
  5. The training split has 1,600 reviews. After truncation at 600 tokens, a review has approximately 554 tokens on average. Approximately how many times does the average vocabulary row get an update in one epoch? What does that mean for the rare half of the vocabulary?
Worked solution

1. $10{,}000 \times 64 = \mathbf{640{,}000}$.

2. None. A mean has nothing to learn. Note this: the full "architecture" here is a lookup and then an average.

3. $64 \times 1 + 1 = \mathbf{65}$.

4. $640{,}065$, and the embedding is 99.99% of it. Almost the full model is a lookup table that does no calculation. Thus overfitting will come from the embedding and from nowhere else. The useful controls are the ones that change it: make the vocabulary smaller, make $d$ smaller, initialize from pretrained vectors, or freeze it. The classifier head is 0.01% of the parameters. If you tune it, nothing will change.

5. Approximately $1{,}600 \times 554 \approx 886{,}000$ token occurrences over 10,000 rows. That is an average of approximately 89 updates for each row in each epoch. But word frequencies follow Zipf's law, so that average is misleading. The top few hundred rows get most of the updates. The bottom half of the vocabulary can get one or two updates in the full run. Those rows stay almost at their random initialization. Chapter 07 gives the same argument from the backward pass: a row that is never looked up gets exactly zero gradient.

In the wild

Word-level vocabularies with an <UNK> bucket are a teaching tool. Production text pipelines use subword tokenization, which has no unknown tokens. Each string divides into pieces that are in the vocabulary: 

from tokenizers import Tokenizer, models, trainers, pre_tokenizers

tok = Tokenizer(models.BPE(unk_token=None))
tok.pre_tokenizer = pre_tokenizers.ByteLevel()
tok.train_from_iterator(corpus, trainers.BpeTrainer(vocab_size=8000))

tok.encode("antidisestablishmentarianism").tokens
# ['anti', 'dis', 'establish', 'ment', 'arian', 'ism']  — nothing is <UNK>

The results are more than coverage. A byte-level BPE vocabulary can encode any byte string. That is why a modern model can read code, emoji and languages that it never saw in training. It also separates the vocabulary size from the vocabulary of the corpus. Thus the embedding table becomes a design choice, not a result of your data. Building BPE from scratch is the first extension in Chapter 12. It is the largest gap between this course and a production language model.

Feel for the numbersMust do

One tensor controls the size of a text model, and it is not the tensor that does the work. Learn to calculate these sizes before you write any code.

Now do these on paper. Where you can, do them in your head.

  1. $V = 20{,}000$ and $d = 100$. How many parameters are in the embedding? How many are in a Linear(100, 2) head? What is the ratio?
  2. Your model reports 51% test accuracy on this balanced corpus. What have you learned? What is the first thing to check?
  3. You halve the vocabulary from 20,000 to 10,000. What happens to the parameter count? What happens to the words that you dropped?
Answers

1. $2{,}000{,}000$ against $202$. The ratio is approximately 9,900 to 1. Almost each parameter in the model is in a lookup table.

2. Nothing at all. On a balanced two-class problem, 50% is chance. Thus 51% is chance plus noise. First, check that the labels really get to the loss. Overfit eight examples, and see if you can get the loss to zero. If you cannot, the bug is in the wiring, not in the learning.

3. The embedding becomes 1,000,000, so the model becomes approximately 50% smaller. The dropped words all become <UNK>. Thus the model cannot tell them apart. This is usually a good trade, because a word that occurs two times in training has an embedding that is mostly noise.

The habit. Count the parameters before you build the layer. Then check with sum(p.numel() for p in layer.parameters()). It takes two seconds, and it finds a transposed dimension immediately.

Say it backRecommended

Explain this to your favorite LLM, in your own words: what does an embedding layer actually do, and why is averaging the embeddings both a reasonable baseline and a dead end? Then ask it to correct you. Ask it to question each part where you were vague, not only the parts where you were wrong, because the gaps are in the vague parts. Do not use the word "vector" in your first two sentences.

What a good answer covers — open this afterwards, not before
  1. An embedding is a lookup table. An integer selects one row. That is the same operation as the product of a one-hot vector and a matrix.
  2. Those rows are parameters. Thus the model learns the geometry from the task. Nobody gives it. Words that this objective uses in a similar way move near each other.
  3. Averaging is a reasonable baseline because sentiment is mostly decided by which words occur. Also, averaging has no parameters of its own that can overfit.
  4. It is a dead end because addition is commutative. Each sequence of the same tokens gives the same vector. Thus negation, scope and long-range structure are not only difficult. The model cannot represent them.
  5. Almost all the parameters are in the table. Thus overfitting comes from there, and each fix must aim at it.

Most common miss. An answer describes the lookup and stops. The interesting half is the limit. If your explanation would also apply to a model that could read word order, it has not found what averaging costs.
